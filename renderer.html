Inside the renderer

A terminal that is doing nothing should cost nothing. Getting there meant finding a 2,984-byte struct being copied hundreds of times per frame, a cache that rebuilt itself every frame to discover nothing had changed, and a rendering bug that both of them had been hiding.

What a frame costs

Sinclair paints its grid as a custom Element on gpui: background quads, then batched shaped text runs, then the cursor. The interesting question is what happens on the second frame, when most of the screen is identical to the first.

The obvious answer is to lay the whole grid out again. It is simple, it is always correct, and it is what gpui's own terminal does — its layout_grid runs fresh from prepaint and produces its rectangles and text runs per frame, with no cross-frame row cache anywhere in the file. For an editor with a terminal panel in the corner, that is a perfectly sensible trade.

Sinclair leans harder on the terminal being the whole window, so it adds a layer gpui's does not have: a cross-frame row cache. Each visible row becomes a RowSnapshot held behind an Rc, reused across frames in one of two ways — by viewport index when the terminal's per-row damage says the row is untouched, or matched by revision after a scroll has rotated rows into new slots. vt's Row::revision, a process-wide counter bumped on every touch(), exists purely so the renderer can recognize a row it has already resolved.

Measured on a 200×50 grid, release build:

FrameSnapshot cost
Idle — no damage, whole-snapshot reuse71 ns
Scrolled — one new line, rest re-homed17.4 µs
Full rebuild — every cell re-resolved91.2 µs

Row reuse is worth roughly 5× on scrolling output, and the idle path is effectively free. That last number is what makes the rest of this page embarrassing.

The 2,984‑byte struct

gpui's ShapedLine is 2,984 bytes. Not because a shaped line of text is large, but because its decoration_runs field is a SmallVec<[DecorationRun; 32]> — thirty-two runs of inline capacity, sitting in the struct whether you use them or not. A terminal span only ever has one decoration run.

prepaint was copying one of those per span into the frame's draw list, plus a throwaway Vec per row. On a 200×50 grid that is roughly 450 KB memcpy'd and allocated every frame — including idle frames, where the snapshot layer above it had just finished its work in 71 nanoseconds. The cache was doing its job perfectly and then handing off to a loop that undid the benefit.

The fix is unglamorous: share the shaped lines by Rc and build the draw list in a single exact-capacity pass. The per-span entry went from 2,992 bytes to 16.

The general lesson. Never store a ShapedLine by value in a per-frame collection. Its size is dominated by inline capacity you are not using, and size_of is the only way you will ever find out — it does not show up as an obvious hot loop in a profile, just a uniformly slightly-too-slow frame.

The cache that rebuilt itself to learn nothing

A second cache sits below the first: shaped rows keyed by RowSnapshot pointer identity, so a row that survives a scroll keeps its shaped text instead of being re-shaped in its new slot.

Every frame, it drained the entire Vec<Option<ShapedRow>> into a fresh HashMap<*const RowSnapshot, ShapedRow>, then rebuilt the vector from the map. On the overwhelmingly common frame where nothing scrolled, it did all of that to discover that every row was exactly where it had left it.

Now unmoved rows settle in place with a single pointer compare, and only rows that actually moved go through the map — which is the scroll case the re-homing exists for in the first place. A 50-row idle frame went from 3.9 µs and an allocation to 74 ns and none, about 53×.

That logic lives in realign_shaped_rows, a free function, specifically so it can be tested without standing up a window — including the duplicate-row case, which is the one that bites.

The bug underneath

Row reuse shipped before this, and it shipped with a defect worth describing, because it is the natural failure mode of the whole approach.

A scroll rotates row objects into new viewport slots. The renderer re-homes them by revision, so an unchanged row is neither re-resolved nor re-shaped — that is the point. But each row's primitives (BgRun, Span, BoxCell) baked in the row index they were first built at, and paint positioned by that stored index rather than the row's current slot.

So a reused row kept painting at its original y for as long as it survived on screen, drifting further from its real slot with every scroll it lived through, until several rows landed on the same y and composited their glyphs on top of one another. Fast scrolling output that reuses rows across many frames — brew upgrade, a build log — turned into unreadable overlapping text. Slow output looked perfect.

The fix was to delete the row index from all three primitives. A row's position is now its index in Snapshot::rows and nothing else, so no per-row copy exists that a scroll can make stale; the paint layers take the slot from enumerate().

The invariant. Never store a row or viewport index inside a RowSnapshot or its primitives. Reuse moves those objects between slots, and any index they carry is a copy that reuse can invalidate.

Testing a cache you cannot see

A rendering cache fails by looking right most of the time, which makes example-based tests nearly useless. The guard is differential: two terminals are fed identical bytes, one driven through the real damage tracking and row reuse, the other rebuilt from scratch at every step, and their rows, cursor, and offset are asserted equal.

The corpora cover scrolling, cursor-addressed redraws, styled/wide/box-drawing cells, alt-screen switches and scrollback changes, plus a seeded fuzz over six seeds and six hundred steps each. A missed damage mark or a bad reuse key cannot hide behind being usually correct.

The overlap bug also earned a dedicated regression test that asserts painted quad geometry rather than text placement. That distinction matters: the row objects were always in the correct slots, so a test checking which text landed in which slot passed the whole time. Only the baked index was stale, and only the background quads' coordinates revealed it.

What is still there

Known remaining per-frame costs, all currently judged not worth the churn — listed because the useful version of a performance page is the one that admits what it has not fixed:

  • Frame is about 6,160 bytes, because the cursor glyph and ghost still hold a ShapedLine by value — once per frame each, rather than once per span.
  • Pointer registration boxes four closures per frame.
  • The snapshot key clones the search query string every frame while search is open.
  • Building a snapshot fills a 256-entry palette-override array per rebuild.

Sinclair exposes the counters to check any of this yourself: SnapCache::stats() reports frames, whole-snapshot reuse, resolved rows and shaped rows, so shaped_rows / frames tells you directly how much reuse you are actually getting on your workload. See performance.md for the full set and the resource budgets around them.
